# Terraform

Infrastructure managed as code. Today that is Authentik's configuration: everything the repo customises, which
used to be a blueprint applied by the `deploy-authentik-config` release job.

```
versions.tf    Terraform and provider versions
backend.tf     where state lives: an Oracle Object Storage bucket (see Remote state)
providers.tf   provider settings
variables.tf   inputs; secret ones come from GitHub secrets as TF_VAR_*
main.tf        (empty: the resources are in the files below)
imports.tf     id lookups and `local.ids`, for the import blocks next to each resource
recovery.tf    the password recovery flow and its stages
enrollment.tf  the sign-up flow and its stages, and the policy that gates it (policies/)
login.tf       the login flow's title, passkey login, the brands
google.tf      the Google login source and its two flows
bindings.tf    which stages each flow runs, and the policy bindings
applications.tf  the Broker, Logs and Metrics proxy providers and apps, and the embedded outpost
scripts/       authentik_ids.py, the read-only lookup behind imports.tf
.terraform.lock.hcl   provider checksums; committed
```

## What it owns, and what it leaves alone

Only what the old blueprint set. Authentik's own blueprints still create the stock flows, stages and policies,
so many resources here are *imported* stock objects with a few attributes overridden. Terraform doesn't
touch the rest of those objects: each attribute the blueprint never set is under `ignore_changes`, so
Terraform leaves it as Authentik has it. Users, groups and their members, tokens and passkeys are not here.

The Broker app deliberately has no group binding: sign-up lets any new user reach `/pair`. Logs and Metrics are
bound to the `authentik Admins` group.

A proxy provider is also an OAuth2 provider (one object in Authentik), so Logs and Metrics have two resources
each on the same provider: `authentik_provider_proxy` for the proxy side and `authentik_provider_oauth2` for the
pinned client id and secret and the grants. They are imported with the same id. Saving the proxy side resets the
grants to Authentik's defaults, so the OAuth2 resource `depends_on` the proxy one and is always applied after it.

Two limits of the provider, worth knowing when a plan looks odd:

- A provider's scope mappings and a source's client secret are not read back, so they always show as a change
  on the first plan. The change sets the value that is already there.
- Authentik returns many-to-many lists (a prompt stage's fields, the MFA stage's setup stages, the outpost's providers) in no fixed
  order, so the first plan can show them reordered. One apply puts them in the configured order and later plans
  are clean.

## The first plan and apply: imports

Almost every object already exists in Authentik, so each resource has an `import` block and the first plan imports
instead of creating. The ids are generated by Authentik, so `scripts/authentik_ids.py` looks them up by name
from the live server (read-only, with `AUTHENTIK_TOKEN`) and `imports.tf` exposes them as `local.ids`.
The exception is the Google login flows (`broker-source-authentication`, `broker-source-enrollment`) with their
stage and policy bindings: the live server never got them, so the first apply creates them and switches the Google
source over to them. Everything else should show as an import, plus the few changes listed above, and no destroys.
After one apply has put everything in the state, the import blocks do nothing and can be deleted; `local.ids` is
still used to find stock objects by name.

## Remote state

State lives in an Oracle Cloud Object Storage bucket, through its S3-compatible API (`backend.tf`). Local state on a
CI runner would be thrown away with it, and Terraform would lose track of what it imported, so the apply job refuses
to run without a bucket. One-time setup in Oracle Cloud:

1. Create a private bucket, e.g. `auth-broker-tfstate`, and turn on versioning so an earlier state can be restored.
2. Create a customer secret key for a user that may manage objects in that bucket (Profile > User settings >
   Customer secret keys); it gives an access key and a secret.
3. Note your Object Storage namespace (Tenancy details) and the bucket's region.

Then add these in the repo's Settings > Secrets and variables > Actions, and nothing else about the bucket is committed:

| Variable | Value |
| --- | --- |
| `TF_STATE_BUCKET` | the bucket name |
| `TF_STATE_REGION` | its region, e.g. `eu-frankfurt-1` |
| `TF_STATE_ENDPOINT` | `https://<namespace>.compat.objectstorage.<region>.oraclecloud.com` |

The access key and secret go in the secrets `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` (the names the S3 backend
reads). To plan from your own machine, export those two and run `terraform init` with the same three values as
`-backend-config="bucket=..."`, `-backend-config="region=..."` and `-backend-config='endpoints={s3="..."}'`.
State locking is not turned on (it isn't confirmed to work on Oracle's S3 API), so the workflow's concurrency group keeps applies to one at a time instead.

Oracle's S3 API refuses the chunked, checksummed upload the AWS SDK sends by default (`501 AWS chunked encoding not
supported`), so the workflow sets `AWS_REQUEST_CHECKSUM_CALCULATION` and `AWS_RESPONSE_CHECKSUM_VALIDATION` to
`when_required`. Export both too when you run Terraform from your own machine. Terraform saves state only at the end of
an apply, after Authentik has changed, so the apply job first writes and removes a throwaway workspace in the bucket
and stops there if that fails. If an apply still can't save, the job attaches `errored.tfstate` as the
`errored-tfstate` artifact for a day: `terraform state push errored.tfstate` puts it back. Losing state that way is
recoverable: a plan imports what exists again, and objects an interrupted apply already created are adopted, not
duplicated.

## Secrets

Repository secrets (Settings > Secrets and variables > Actions), none of them in a file:

| Secret | What |
| --- | --- |
| `AUTHENTIK_TOKEN` | An Authentik API token (Directory > Tokens, for a dedicated service account). Plans only read, so the repository secret can be a read-only token; add one that may write as a secret of the `terraform` environment, which apply uses instead. |
| `TF_VAR_GOOGLE_CLIENT_ID`, `TF_VAR_GOOGLE_CLIENT_SECRET` | The Google login source's OAuth client (they were `BLUEPRINT_GOOGLE_*` in `secrets/authentik.env`). |
| `TF_VAR_LOGS_CLIENT_SECRET`, `TF_VAR_METRICS_CLIENT_SECRET` | The Logs and Metrics providers' client secrets (`BLUEPRINT_LOGS_CLIENT_SECRET`, `BLUEPRINT_METRICS_CLIENT_SECRET`). |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | The state bucket's customer secret key (see [Remote state](#remote-state)). |

Without `AUTHENTIK_TOKEN` and the bucket's key the plan is skipped (the other checks still run). A saved plan contains the
secret values, so the plan artifact `apply` uses is kept for a day only.

## Changing Authentik's configuration

1. Edit the `.tf` files. `terraform fmt`, `terraform validate` and `tflint` run on commit if you have pre-commit
   installed (`pre-commit install`; needs `terraform` and `tflint` on your PATH).
2. Open a PR. Checks run in parallel: formatting and validation, tflint, a Trivy misconfiguration scan, and a
   plan against the live Authentik, which is posted as a comment on the PR and updated on each push.
3. Stock objects are looked up by name through `local.ids`. A new attribute on an imported stock object is
   written like the others; one the config doesn't set stays as Authentik has it, which is what
   `ignore_changes` is for.

To add a provider, add it to `required_providers` in `versions.tf` with a `~>` constraint, then record its
checksums for CI and your own machine and commit the lock file:

```sh
cd terraform
terraform init -backend=false
terraform providers lock -platform=linux_amd64 -platform=darwin_arm64
```

## Applying

After the PR is merged: Actions > Terraform > Run workflow on main, with "apply" ticked. It reruns the checks,
plans main (the plan is in the run's summary), then waits for approval in the `terraform` environment. Approving
applies exactly that plan; if anything changed the state in between, Terraform rejects it as stale and nothing is
applied. Without "apply" ticked, the button just plans, which shows any drift.

The `terraform` environment needs a required reviewer (Settings > Environments). Without the environment GitHub
creates it on the first run with no protection, and apply would run unapproved.

## Upgrading

The Authentik provider's versions follow Authentik's (`2026.8.x`), so
bump `AUTHENTIK_VERSION` in `docker-compose.yml` and the provider together. Dependabot opens PRs for providers
and modules. Terraform itself is pinned in `versions.tf` and in `TF_VERSION` in the workflow; bump both together.
